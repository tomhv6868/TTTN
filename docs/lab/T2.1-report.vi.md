# Báo cáo T2.1 — Parser C++ dùng chung

## Trạng thái

T2.1 đã đạt điều kiện nghiệm thu kỹ thuật và được người dùng chọn **Chấp nhận** ngày 2026-07-15. Biên nhận `run_log/t2.1/acceptance.json` có trạng thái `passed` trên Ubuntu 24.04 x86_64 với Python 3.12.3 và GNU C++ 13.3.0.

Clean Release build hoàn tất 13/13 bước. CTest 5/5 và toàn bộ 128 Python unittest đều đạt. Năm hash source, bốn hash command log và bản sao receipt trong thư mục attempt đã được đối chiếu với file thực tế; không có sai lệch. T2.1 được đóng; T2.2 chỉ bắt đầu sau cổng xác nhận riêng về phạm vi, đầu vào và tiêu chí nghiệm thu.

## Bằng chứng dùng để khóa phạm vi

Không quét lại thủ công hoặc đọc từng packet của CIC-IDS2017. Chương trình streaming T1.1 đã xử lý tự động đủ 56.370.702 packet trong năm file PCAPNG và ghi aggregate receipt tại `run_log/t1.1/pcap-inventory.json`.

Kết quả đã có cho thấy:

- toàn bộ packet dùng linktype Ethernet;
- 52.101.890 packet TCP và 3.851.999 packet UDP;
- 298 packet có IPv4 options và 15.822.675 packet có TCP options;
- 2.060 IPv4 fragment phải bị từ chối theo Packet Contract;
- `vlan_depth_counts` chỉ có độ sâu 0, nên dataset không cung cấp bằng chứng thực nghiệm để chọn VLAN TPID.

Parser production đồng bộ với tập TPID mà chương trình inventory T1.1 đã dùng: `0x8100`, `0x88A8` và `0x9100`. Parser nhận tối đa một tag và trả `nested_vlan` khi inner EtherType tiếp tục là một VLAN TPID. Đây là quyết định thiết kế để giữ cùng semantics giữa inventory và production; không phải kết luận rút ra từ packet VLAN trong CIC-IDS2017.

## Kiến trúc

```text
PCAPNG adapter ─┐
                ├─> PacketInput{byte span, timestamp, wire length}
DPDK adapter ───┘                   │
                                    v
                              parse_packet()
                                    │
                                    v
                           PacketView hoặc ParseError
```

`cpp/src/packet.cpp` chỉ nhận `PacketInput` và trả `ParseResult<PacketView>`. File không include libpcap, DPDK, Scapy hoặc API adapter. `PacketView` tiếp tục là vùng nhìn không sở hữu trên byte span đầu vào; parser không sao chép raw frame và bên gọi phải giữ vùng đệm nguồn còn sống.

Đường PCAPNG và DPDK ở T2.4/T2.5 phải gọi đúng parser này. T2.1 không đọc file PCAPNG, không nhận `rte_mbuf`, không tạo flow và không tính feature.

## Phạm vi đã triển khai

### Thành công

- Ethernet II và địa chỉ MAC theo thứ tự byte trên đường truyền;
- không VLAN hoặc đúng một VLAN tag với TPID `0x8100`, `0x88A8` hay `0x9100`;
- IPv4 không phân mảnh, IHL biến đổi và options;
- TCP với data offset biến đổi, options, port, sequence, acknowledgement, window và đủ chín flag;
- UDP với datagram length hợp lệ;
- payload rỗng hoặc có dữ liệu;
- payload kết thúc theo độ dài IPv4/TCP hoặc UDP, không ăn Ethernet padding hay byte IPv4 nằm ngoài UDP datagram;
- capture có thể ngắn hơn `wire_length` nhưng vẫn parse thành công nếu toàn bộ IPv4 datagram cần thiết còn hiện diện.

Checksum Ethernet, IPv4, TCP và UDP không được xác minh. Packet Contract T1.1 không cung cấp error code checksum; ngoài ra checksum offload có thể làm checksum trên byte capture chưa phản ánh giá trị cuối trên wire. Việc không kiểm checksum được khóa rõ trong acceptance contract thay vì bị bỏ sót ngầm.

### Lỗi có kiểu

| Layer | ParseErrorCode |
|---|---|
| Input | `inconsistent_lengths`, `unsupported_link_layer` |
| Ethernet | `truncated_ethernet_header`, `unsupported_ether_type` |
| VLAN | `truncated_vlan_header`, `nested_vlan` |
| IPv4 | `truncated_ipv4_header`, `invalid_ipv4_version`, `invalid_ipv4_header_length`, `truncated_ipv4_packet`, `invalid_ipv4_total_length`, `fragmented_ipv4`, `unsupported_transport_protocol` |
| TCP | `truncated_tcp_header`, `invalid_tcp_header_length` |
| UDP | `truncated_udp_header`, `invalid_udp_length` |

Mỗi test lỗi đối chiếu cả `kind`, `layer`, `code`, `offset`, `available` và `required`. IPv4 fragment bị phân loại `unsupported`; header hoặc packet thiếu byte là `truncated`; trường version/length mâu thuẫn là `malformed`.

## Dữ liệu kiểm thử

`cpp/tests/packet_parser_test.cpp` chứa hai frame byte nhỏ, bất biến:

- Ethernet/IPv4/TCP có IPv4 options, TCP options và payload;
- VLAN/IPv4/UDP có payload.

Test tạo bản sao cục bộ rồi thay đúng trường cần kiểm tra để sinh malformed/truncated cases. Các byte này là fixture kiểm thử parser, không phải parser thứ hai, không có label và không được dùng làm dữ liệu train. Test còn kiểm tra ba VLAN TPID, toàn bộ TCP flag, payload rỗng, IPv4 byte dư sau UDP datagram và đủ 17 error code.

## Script kiểm tra và receipt

`scripts/verify_t21_packet_parser.py` cung cấp ba lệnh:

- `check`: kiểm tra source contract mà không build hoặc ghi artifact;
- `run`: trên Ubuntu 24.04 x86_64/Python 3.12, tạo clean Release build ngoài shared source, chạy toàn bộ CTest và Python unittest, hash source/log rồi chỉ ghi acceptance cuối khi mọi gate đạt;
- `validate`: kiểm tra schema và tính nhất quán của receipt đã lưu.

Script từ chối root, host sai, artifact root ngoài `run_log/t2.1/` và ghi đè `acceptance.json`.

## Lệnh tái lập nghiệm thu trên Ubuntu sensor

Chạy bằng user thường từ workspace shared:

```bash
cd /mnt/hgfs/TTTN
source "$HOME/.local/nids-toolchain/env.sh"
python3 -B scripts/verify_t21_packet_parser.py check
python3 -B scripts/verify_t21_packet_parser.py run
```

Khi `run` đạt, xác minh lại receipt:

```bash
python3 -B scripts/verify_t21_packet_parser.py validate \
  --input run_log/t2.1/acceptance.json
```

Receipt cuối phải có `status: passed`, CTest phải chứa `nids_core.packet_parser`, mọi CTest phải đạt và toàn bộ Python unittest phải trả mã 0. Trình nghiệm thu không ghi đè receipt cũ; muốn chạy lại phải lưu artifact hiện tại vào lịch sử trước.
